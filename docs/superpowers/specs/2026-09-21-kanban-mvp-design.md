# MVP Kanban для распределения заявок

## 1. Цель

Создать рабочее веб-приложение для ежедневного распределения заявок на переговоры между менеджерами по продажам офисной мебели. Система должна максимизировать суммарную ожидаемую валовую маржу, учитывать ограниченную вместимость менеджеров и оставлять окончательное решение под контролем сотрудника.

Приложение должно запускаться локально в VS Code на демонстрационных данных без обязательных внешних ключей. Архитектура должна позволять позднее подключить Supabase, Render и Netlify без переделки пользовательского интерфейса.

## 2. Границы MVP

Входит в MVP:

- авторизация одного типа пользователя: сотрудник с доступом ко всей доске;
- демо-набор из пяти менеджеров, пяти регионов, трёх категорий товаров и примерно 70 входящих заявок;
- динамическое количество менеджеров и заявок в рабочем режиме;
- добавление менеджеров через интерфейс/API;
- статическое добавление заявок в первом MVP с подготовленным контрактом для будущего сервиса или импорта;
- исторические данные по переговорам и продажам;
- расчёт эффективности менеджеров по региону и продукту;
- временное взвешивание свежих и исторических результатов;
- сглаживание малых выборок;
- расчёт Expected GM для каждой пары «заявка — менеджер»;
- оптимальное назначение с учётом индивидуальной вместимости менеджеров и настраиваемого общего лимита, если он задан;
- Kanban-доска с drag-and-drop;
- ручная корректировка назначения;
- объяснение рекомендации и изменение Expected GM;
- REST API на Node.js + Express + TypeScript;
- отдельный Python-слой для аналитики и OR-Tools-ready оптимизации;
- локальный demo data source;
- SQL-схема и seed для будущего Supabase;
- тесты ключевых расчётов и ограничений;
- инструкции запуска и конфигурация для будущего Render/Netlify.

Не входит в MVP:

- интеграция с CRM;
- реальные платежи или биллинг;
- сложная ML-модель, требующая обучения в production;
- роли администратора и менеджера;
- Power BI/Metabase;
- автоматическая отправка уведомлений;
- production-развёртывание без предоставленных учётных данных.

## 3. Архитектура

Проект организуется как monorepo:

```text
frontend/   React + TypeScript + Vite + Tailwind + dnd-kit
backend/    Node.js + Express + TypeScript + REST API
analytics/  Python + pandas + статистические расчёты + OR-Tools adapter
supabase/   SQL schema + seed + будущие миграции
docs/       спецификация и инструкции
```

Frontend общается только с REST API. Backend содержит доменные типы, авторизацию демо-пользователя, валидацию запросов, работу с источником данных и сохранение ручных изменений. Источник данных выбирается конфигурацией: локальный demo repository по умолчанию, Supabase repository после настройки окружения. Число заявок и менеджеров не ограничивается фиксированными значениями в коде.

Python-слой не является обязательным для локального запуска UI. Node backend использует общий алгоритмический контракт; сначала он может выполнять прозрачный MVP-расчёт локально, а Python/OR-Tools подключается через отдельный адаптер или CLI/API без изменения frontend-контракта.

## 4. Авторизация

В MVP используется одна роль `employee`. Локальный режим предоставляет тестовый аккаунт и сессию для разработки. Контракт аутентификации должен быть совместим с последующим Supabase Auth: frontend хранит сессию, backend проверяет токен и возвращает 401 для неавторизованных запросов.

Тестовый пользователь должен быть явно обозначен в README и не использоваться как production-секрет.

## 5. Модель данных

Основные сущности:

- `managers`: имя, email, активность, дневная вместимость, дата создания;
- `leads`: регион, продукт, источник, статус, потенциальная сумма, дата создания;
- `negotiation_history`: дата, менеджер, регион, продукт, состоялся ли разговор, была ли продажа, сумма продажи, GM, скидка;
- `lead_assignments`: заявка, менеджер, Expected GM, вероятность, источник назначения, время назначения;
- `manager_statistics`: агрегаты по менеджеру, региону и продукту;
- `optimization_runs`: время запуска, количество заявок, назначенных заявок и суммарная Expected GM;
- `users`/auth metadata: идентификатор сотрудника и роль при подключении Supabase Auth.

Демо-данные должны включать разные сильные стороны менеджеров, регионы и продукты, чтобы рекомендации были объяснимыми и визуально различимыми.

## 6. Алгоритм

Для пары менеджер–регион–продукт рассчитываются:

- число состоявшихся переговоров;
- число продаж;
- конверсия;
- средний чек;
- средняя GM при продаже;
- средняя скидка;
- GM на переговор.

Свежесть учитывается временным весом: последние 14 дней получают повышенный вес, исторический период используется как стабилизатор. MVP допускает конфигурируемые веса, по умолчанию 60% для свежего периода и 40% для исторического.

При малом количестве наблюдений индивидуальная статистика смешивается с более общими уровнями: менеджер + регион + продукт, менеджер + продукт, регион + продукт, продукт и общая команда. Чем больше наблюдений, тем больше вес индивидуальной статистики.

Для каждой пары заявки и менеджера рассчитываются:

```text
Expected GM = P(продажи) × Expected GM при продаже
```

Оптимизатор выбирает набор назначений с максимальной суммой Expected GM при ограничениях:

- заявка назначается максимум одному менеджеру;
- менеджер получает не больше собственной дневной вместимости;
- общий лимит назначений является настраиваемым и по умолчанию равен сумме вместимостей активных менеджеров;
- заявки с низкой ценностью могут остаться в колонке `Не назначено`.

Ручное назначение не удаляет алгоритмическое объяснение: UI показывает рекомендованного менеджера, текущего менеджера и разницу ожидаемой GM.

## 7. Пользовательский интерфейс

Основной экран — рабочая Kanban-доска без крупных маркетинговых заголовков.

Состав экрана:

- компактная верхняя панель: название рабочего пространства, текущая дата, пользователь, выход;
- панель KPI: входящие заявки, назначено, не назначено, Expected GM;
- фильтры по региону, продукту, статусу и поиску;
- динамическое число колонок менеджеров с загрузкой `назначено / вместимость`;
- отдельная колонка `Не назначено`;
- карточки заявок с номером, регионом, продуктом, Expected GM, вероятностью и текущим менеджером;
- боковая панель или модальное окно деталей заявки;
- кнопка `Рассчитать распределение`;
- состояния загрузки, ошибки и пустого результата.

Дизайн: industrial minimal — графитовый текст, нейтральный фон, один янтарный акцент, компактная типографика, чёткие границы колонок, цветовая индикация Expected GM и загрузки. Интерфейс русскоязычный, суммы отображаются в BYN. Должны быть видимые focus-состояния и базовая клавиатурная доступность.

## 8. REST API

Минимальный контракт:

- `POST /api/auth/login` — вход в demo-режиме;
- `POST /api/auth/logout` — завершение сессии;
- `GET /api/me` — текущий пользователь;
- `GET /api/managers` — менеджеры и загрузка;
- `POST /api/managers` — добавление менеджера;
- `PATCH /api/managers/:id` — изменение менеджера и вместимости;
- `POST /api/leads` — добавление заявки в статическом MVP-режиме;
- `GET /api/leads` — заявки с фильтрами;
- `GET /api/leads/:id` — заявка с объяснениями и оценками по менеджерам;
- `POST /api/optimization-runs` — запуск расчёта;
- `GET /api/optimization-runs/:id` — результат расчёта;
- `PATCH /api/leads/:id/assignment` — ручное назначение;
- `GET /api/dashboard/summary` — KPI доски.

Все изменяющие запросы требуют авторизации. Ошибки возвращаются в едином JSON-формате с кодом и понятным сообщением.

## 9. Проверка

Backend-тесты проверяют:

- формулу Expected GM;
- временное взвешивание;
- сглаживание малых выборок;
- максимальную вместимость каждого менеджера;
- настраиваемый общий лимит назначений;
- отсутствие двойного назначения заявки;
- корректность ручного перераспределения.

Frontend проверяется сборкой TypeScript и ручным smoke-тестом: вход, загрузка доски, запуск оптимизации, drag-and-drop, просмотр объяснения, ручное назначение, выход.

## 10. Развёртывание и переменные окружения

Локальный запуск не требует Supabase. `.env.example` содержит demo-настройки и заготовки для:

- `VITE_API_URL`;
- `PORT`;
- `DATA_SOURCE=demo|supabase`;
- `SUPABASE_URL`;
- `SUPABASE_ANON_KEY`;
- `SUPABASE_SERVICE_ROLE_KEY` только для backend и только через секреты окружения.

Frontend готовится к Netlify через build-команду и redirect для SPA. Backend готовится к Render через start/build-команды и health endpoint. Секреты не коммитятся.

## 11. Критерии готовности

MVP считается готовым, если:

1. проект запускается в VS Code по README;
2. сотрудник может войти в demo-режиме;
3. на доске отображаются демо-заявки и seed-менеджеры;
4. запуск оптимизации распределяет заявки с учётом вместимости всех активных менеджеров;
5. карточки можно перемещать между колонками;
6. после ручного переноса видна разница Expected GM;
7. ключевые тесты проходят;
8. Supabase schema/seed готовы к подключению и допускают добавление менеджеров и заявок без изменения схемы;
9. frontend собирается для Netlify, backend собирается и запускается для Render;
10. интерфейс остаётся компактным, рабочим и без крупных заголовков.
